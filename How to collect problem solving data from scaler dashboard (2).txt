# Scaler++ — Scaler API & Historical Problem Activity Discovery

> **Status:** Discovery validated  
> **Discovery date:** 27 July 2026  
> **Purpose:** Preserve everything discovered while investigating whether Scaler++ can build a GitHub-style contribution/activity graph from a student's historical Scaler activity.
>
> This document exists so that the API-discovery work does **not need to be repeated manually** in DevTools.

---

# 1. Why We Investigated This

The Scaler student dashboard has a large amount of unused space on the main Practice/dashboard page.

The proposed Scaler++ feature is a GitHub-style activity/contribution calendar showing a student's academic/problem-solving activity.

Conceptually:

```text

Mon   ■ □ ■ ■ □ □ ■ ■ ■ □ □ 
Tue   □ ■ ■ □ □ ■ ■ ■ □ □ ■ 
Wed   ■ ■ ■ ■ □ □ □ ■ ■ ■ □ 
Thu   □ □ ■ ■ ■ □ ■ ■ □ ■ ■ 
Fri   ■ ■ ■ □ ■ ■ ■ □ □ ■ ■ 
Sat   □ ■ □ □ ■ ■ ■ ■ □ □ □ 
Sun   ■ □ ■ ■ □ □ ■ □ ■ ■ ■ 

      Less  □ ░ ▒ ▓ ■  More
```

Potential statistics underneath could include:

- Problems solved
- Problems attempted
- Total submissions
- Successful submissions
- Failed submissions
- Current streak
- Longest streak
- Active days
- Problems solved this week/month/year
- Average problems per active day
- Programming-language usage
- Runtime/memory statistics
- Score statistics
- First-attempt success rate
- Attempts required before solving
- Other useful academic/activity metrics

The major technical question was:

> **Can Scaler++ reconstruct activity from BEFORE the browser extension was installed?**

If Scaler only exposed current aggregate counts such as `48 / 49 problems solved`, then historical activity would be impossible to reconstruct accurately.

In that case Scaler++ would have needed to start recording events locally from the installation date.

However, the investigation showed that **Scaler exposes historical submission records containing timestamps**.

Therefore historical reconstruction appears possible.

# 2. Final Discovery

## YES — Scaler exposes historical submission timestamps

A user-submission object returned by Scaler contains fields such as:

```json
{
  "id": 285022548,
  "submission_content": "...",
  "created_at": "2026-03-04T15:29:03.000Z",
  "programming_language": "Java 8 (array support)",
  "programming_language_id": 510,
  "time": 488,
  "memory": 59536,
  "status": "correct_answer",
  "time_unit": "ms",
  "memory_unit": "KB",
  "score": 300.0,
  "logs": null,
  "lab_session_log": null,
  "submission_download_url": null
}
```

The critical field is:

```json
"created_at": "2026-03-04T15:29:03.000Z"
```

This gives an exact historical timestamp for a submission.

Therefore Scaler++ can potentially reconstruct historical activity instead of tracking only activity performed after installation.

# 3. Important Distinction: Submission Time vs `time_to_solve`

During the investigation, an API response was found containing:

```json
{
  "id": 215577879,
  "submission_id": 297082275,
  "submission_result": "correct_answer",
  "has_solved": true,
  "no_of_attempts_left": 0,
  "achieved_score": 75.0,
  "time_to_solve": 80
}
```

Initially, `time_to_solve` looked potentially useful for determining when something was solved.

It is **not the historical timestamp we need**.

It describes some duration/solve metric associated with the problem attempt.

The useful historical timestamp comes from the user-submissions endpoint:

```json
"created_at": "2026-06-10T15:08:23.000Z"
```

Therefore:

```text
time_to_solve
    ≠
historical solve date/time
```

Use:

```text
created_at
```

for the activity calendar.

# 5. User Submissions API

The most important endpoint discovered was:

```text
GET /api/v2/tests/{test_id}/problems/{problem_id}/user_submissions
```

Observed example:

```text
https://www.scaler.com/api/v2/tests/1254633/problems/15992/user_submissions?page=1&per_page=100
```

Generalized:

```text
https://www.scaler.com/api/v2/tests/<TEST_ID>/problems/<PROBLEM_ID>/user_submissions?page=1&per_page=100
```

This endpoint returned historical submission records.

Example response:

```json
{
  "data": [
    {
      "id": "293112145",
      "type": "user_submission",
      "attributes": {
        "id": 293112145,
        "submission_content": "[\"c1 represents shallow copy and c2 represents deep copy\", \"If arr and c1 are printed after line 4 and 7 respectively, they would have printed 12 as first element.\"]",
        "created_at": "2026-06-10T15:08:23.000Z",
        "programming_language": null,
        "programming_language_id": 0,
        "time": 0,
        "memory": 0,
        "status": "correct_answer",
        "time_unit": "ms",
        "memory_unit": "KB",
        "score": 0,
        "logs": null,
        "lab_session_log": null,
        "submission_download_url": null
      }
    }
  ],
  "meta": {
    "current": 1,
    "total": 4
  }
}
```

This confirmed that Scaler stores historical submission data.

# 6. Pagination

The user-submissions response contains:

```json
"meta": {
  "current": 1,
  "total": 4
}
```

Therefore pagination must be handled.

Even though the request can use:

```text
per_page=100
```

the implementation should **not assume one request always contains everything**.

Potential sync logic:

```text
GET ...?page=1&per_page=100

read meta.total

if more pages exist:
    GET page=2
    GET page=3
    ...
```

The exact semantics of `meta.total` should be confirmed during implementation rather than blindly assuming whether it represents pages or another count.

The student's history for this problem was:

```text

    ↓

62 seconds later

2026-03-04 15:29:03 UTC
    ↓
correct_answer
```

Therefore Scaler++ can derive:

```text
Problem: Add Binary Strings

Attempts:             2
Failed attempts:      1
Successful attempts:  1
Final status:         solved
Language:             Java
Successful runtime:   488 ms
Successful memory:    59,536 KB
Accepted timestamp:   2026-03-04T15:29:03Z
```

And approximately:

```text
time from first recorded attempt to accepted submission = 62 seconds
```

Note that this is **not necessarily equivalent to actual time spent solving**. It only measures the interval between the first submission returned and the accepted submission.

# 17. Contribution Calendar Semantics

A critical product decision:

## Do NOT count every submission as a contribution.

For the example above:

```text
15:28:01 → runtime_error
15:29:03 → correct_answer
```

Counting submissions would produce:

```text
March 4 → 2 contributions
```

That would make the graph measure attempts rather than actual solved problems.

Instead, the primary contribution metric should be:

> **Number of distinct problems successfully solved on that date.**

Therefore:

```text
March 4, 2026
Problems solved = 1
```

The failed attempt remains useful for secondary statistics.

# 18. Suggested Definition of "Solved Date"

For each problem:

1. Fetch all historical submissions.
2. Select submissions where:

```json
"status": "correct_answer"
```

3. Determine the earliest accepted submission.
4. Use its:

```json
"created_at"
```

as the problem's solved timestamp.
5. Count that problem exactly once in the contribution calendar.

Pseudo-code:

```javascript
const accepted = submissions
  .filter(s => s.attributes.status === "correct_answer")
  .sort(
    (a, b) =>
      new Date(a.attributes.created_at) -
      new Date(b.attributes.created_at)
  );

if (accepted.length > 0) {
  const solvedAt = accepted[0].attributes.created_at;
}
```

This prevents repeated accepted submissions from artificially inflating the graph.

# 19. Timezone Handling

Scaler returns timestamps like:

```text
2026-03-04T15:29:03.000Z
```

The trailing:

```text
Z
```

means UTC.

The contribution calendar should generally group activity according to the student's local date, not blindly by UTC date.

For an Indian user:

```text
UTC → Asia/Kolkata
```

For example:

```text
2026-03-04T20:00:00Z
```

is:

```text
2026-03-05 01:30 IST
```

Therefore grouping the raw UTC date would incorrectly place that contribution on March 4 instead of March 5.

Implementation should convert timestamps to the appropriate local timezone before determining the contribution date.

# 20. Data Available Per Submission

The discovered submission object gives considerably more information than merely whether a problem was solved.

Fields include:

| Field | Meaning / Potential Use |
|---|---|
| `id` | Unique submission identifier |
| `submission_content` | Submitted answer/code |
| `created_at` | Exact historical submission timestamp |
| `programming_language` | Language used |
| `programming_language_id` | Scaler language identifier |
| `time` | Runtime |
| `memory` | Memory consumption |
| `status` | Submission result |
| `time_unit` | Runtime unit |
| `memory_unit` | Memory unit |
| `score` | Score |
| `logs` | Execution/submission logs when available |
| `lab_session_log` | Lab-related information when available |
| `submission_download_url` | Download URL when available |

Not every field is populated for every problem type.

For MCQ/MSQ problems, for example:

```json
"programming_language": null,
"programming_language_id": 0,
"time": 0,
"memory": 0
```

Therefore analytics code must handle null/zero values correctly.

```text
GET /api/v2/tests/{test_id}/problems/{problem_id}/user_submissions?page=1&per_page=100
```

Example:

```text
/api/v2/tests/1254633/problems/15992/user_submissions?page=1&per_page=100
```

These are currently the two most important endpoint patterns for the contribution feature.

---

# 27. Authentication Model — Current Observation

These APIs were accessed while logged into Scaler through the normal website.

The browser was already authenticated.

Therefore the endpoints appear usable from the authenticated Scaler session.

We have **not yet established**:

- whether there is a documented public API
- whether these internal endpoints are stable
- whether CSRF headers are required for every endpoint
- whether cookies alone are sufficient for all GET requests
- whether extension content scripts can fetch all endpoints directly
- whether host permissions are required
- whether Scaler changes endpoint structures frequently
- what rate limits exist
- whether aggressive crawling could trigger protection

These are implementation questions that still need to be tested.

---

# 28. Important Warning: These Appear to Be Internal APIs

The endpoints discovered through DevTools appear to be APIs used by the Scaler frontend.

That does **not** mean they are a stable public API contract.

Therefore Scaler++ should treat them as potentially unstable.

Implementation should isolate Scaler API logic behind an adapter layer.

Bad architecture:

```javascript
// API URLs scattered everywhere in UI components
fetch("/api/v2/tests/...")
```

Better:

```text
src/
  scaler-api/
    curriculum.js
    classes.js
    tests.js
    submissions.js
```

or:

```text
src/
  services/
    scaler/
      modules.ts
      classes.ts
      tests.ts
      problems.ts
      submissions.ts
```

Then if Scaler changes an endpoint, only the adapter layer needs modification.

# 29. Historical Backfill Strategy

The extension should distinguish between:

```text
INITIAL BACKFILL
```

and:

```text
INCREMENTAL SYNC
```

## Initial backfill

On first setup:

```text
Discover semesters
    ↓
Discover modules
    ↓
Discover classes/topics
    ↓
Discover tests
    ↓
Discover problems
    ↓
Fetch historical submissions
    ↓
Build local activity database
```

This may involve many requests.

Therefore it should happen carefully and progressively.

---

# 30. Incremental Sync

After the historical backfill is complete, Scaler++ should **not repeat the entire crawl on every page load**.

Instead:

```text
Initial installation:
    expensive historical backfill

Normal usage:
    lightweight incremental sync
```

Possible strategy:

```text
lastSync = 2026-07-27T...

on future sync:

    inspect current/recent classes
    inspect current/recent tests
    fetch relevant submissions
    merge unseen submission IDs
```

Submission IDs can help deduplicate records.

# 31. Local Database / Cache

Scaler++ should cache normalized data locally.

Possible conceptual structure:

```json
{
  "version": 1,
  "lastSync": "2026-07-27T...",
  "submissions": {},
  "problems": {},
  "tests": {},
  "activityByDate": {}
}
```

A submission could be normalized as:

```json
{
  "submissionId": 285022548,
  "testId": 1226161,
  "problemId": "...",
  "createdAt": "2026-03-04T15:29:03.000Z",
```

Avoid storing huge duplicate API payloads when only normalized fields are needed.

# 32. Privacy Consideration: Do We Need to Store Submission Code?

The API exposes:

```text
submission_content
```

including complete source code.

The contribution/statistics feature generally does **not need to persist source code**.

Therefore a privacy-conscious implementation should probably store:

```text
submission ID
problem ID
test ID
timestamp
status
language
runtime
memory
score
```

but discard:

```text
submission_content
```

unless a future feature explicitly requires it.

This reduces local storage usage and unnecessary retention of user code.

# 33. Export Data Requirement

Scaler++ must provide an:

```text
Export Data
```

feature.

Reason:

The extension will maintain locally cached/derived analytics.

If the user needs to:

- uninstall the extension
- reinstall the browser
- switch browser profiles
- move to another computer
- reset extension storage

they should not lose the reconstructed/cache data unnecessarily.

The user should be able to export it before uninstalling.

---

# 34. Suggested Export Format

JSON is the best primary backup format.

Example:

```json
{
  "schemaVersion": 1,
  "exportedAt": "2026-07-27T...",
  "scalerPlus": {
    "submissions": [],
    "problems": [],
    "tests": [],
    "activity": {},
    "settings": {}
  }
}
```

Suggested filename:

```text
scaler-plus-backup-2026-07-27.json
```

Later we should also implement:

```text
Import Data
```

so backups can actually be restored.

Export without import would only solve half the problem.

---

# 35. Export vs Reconstructable Data

Some data can theoretically be downloaded again from Scaler.

For example:

```text
historical submissions
```

However, exported backups are still valuable because:

1. internal Scaler APIs may change
2. old curriculum endpoints may stop exposing something
3. the extension may derive statistics not directly stored by Scaler
4. locally recorded events may eventually exist
5. rebuilding everything could require many API requests
6. user preferences/settings need persistence

Therefore export/import should still exist even if historical backfill is available.

# 41. Deduplication Requirements

The extension must avoid double counting.

Useful unique identifiers include:

```text
submission ID
test ID
problem ID
```

For raw submissions:

```text
submission_id
```

should generally be unique.

For solved-problem contributions, use a key conceptually similar to:

```text
testId + problemId
```

and determine its earliest successful submission.

Do not assume problem IDs are globally unique until verified.

Using the pair is safer.

---

# 42. Example Normalization Algorithm

Conceptually:

```javascript
function normalizeSubmission(raw, testId, problemId) {
  const a = raw.attributes;

  return {
    submissionId: a.id,
    testId,
    problemId,

    createdAt: a.created_at,
    status: a.status,

    language: a.programming_language,
    languageId: a.programming_language_id,

    runtime: a.time,
    runtimeUnit: a.time_unit,

    memory: a.memory,
    memoryUnit: a.memory_unit,

    score: a.score
  };
}
```

Then:

```javascript
function getFirstAcceptedSubmission(submissions) {
  return submissions
    .filter(s => s.status === "correct_answer")
    .sort(
      (a, b) =>
        new Date(a.createdAt) -
        new Date(b.createdAt)
    )[0] ?? null;
}
```

---

# 43. Example Activity Aggregation

Conceptually:

```javascript
const activity = {};

for (const problem of problems) {
  const accepted = getFirstAcceptedSubmission(problem.submissions);

  if (!accepted) continue;

  const date = convertToLocalDate(accepted.createdAt);

  activity[date] ??= {
    problemsSolved: 0,
    attempts: 0,
    successfulSubmissions: 0,
    failedSubmissions: 0
  };

  activity[date].problemsSolved++;
}
```

Submission-level statistics can then be aggregated separately.

# 44. Validation Strategy

Historical reconstruction should be validated against the Scaler UI.

Example:

Scaler UI:

```text
Problems Solved
48 / 49
```

Reconstructed data:

```text
47 solved
```

That means something is missing.

Potential causes:

```text
missed test
missed module
missed semester
pagination bug
additional problems omitted
API returned incomplete history
problem-ID collision
status interpretation bug
```

The extension should ideally be able to detect such mismatches during development.

# 45. API Load / Rate-Limit Concern

Historical reconstruction could become request-heavy.

Imagine:

```text
200 tests
×
10 problems each
=
2,000 problem submission requests
```

This should **not** be fired simultaneously.

Do not do:

```javascript
await Promise.all(
  thousandsOfProblems.map(fetchSubmissions)
);
```

That could hammer Scaler's backend and potentially trigger rate limiting.

Instead use:

```text
limited concurrency
caching
incremental sync
request delays if necessary
retry/backoff
```

The exact safe concurrency should be determined experimentally and conservatively.

The following statements are supported by actual observed API responses.

### Proven

- Scaler has internal APIs used by its frontend.
- Tests have IDs.
- Tests expose problem lists.
- Problems have IDs.

- Submission history includes successful and failed attempts.

- Coding submissions can contain runtime information.

- Historical activity from before extension installation is technically available for at least the tested cases.

Do not confuse these with confirmed facts.

### Still needs investigation

- Whether all Additional Problems use the same API pattern.
- Whether contests use the same API pattern.

- Exact API authentication requirements from an extension.
- Whether requests work directly from an extension service worker.
- CORS behavior.
- Required Chrome host permissions.
- Rate limits.
- Endpoint stability.
- Safe request concurrency.
- Exact pagination semantics across all endpoints.
- Every possible submission status.
- Whether deleted/archived problems remain queryable.

- Whether all historical solved counts can be reconstructed exactly.
- Whether the same problem can appear in multiple tests.
- Whether duplicate/reused problems should count once or multiple times.
- Whether Scaler's internal API terms permit all intended extension behavior.

These should remain explicit open questions.

Do not build the UI first.

The difficult part is building a reliable pipeline:

```text
→ cache
```

A contribution grid can be built quickly once reliable normalized activity data exists.

The sync engine is the actual engineering work.

# 62. Failure Handling

Internal APIs can fail.

The extension should eventually handle:

```text

403 / forbidden
404 / endpoint changed
429 / rate limited
5xx / server failure
network offline
malformed response
partial sync
```

A failed sync should **not delete existing local history**.

Preferred behavior:

```text
existing local database
+
successful new records
```

rather than:

```text

→ fetch
→ API fails
→ user now has no data
```

# 108. Updated Recommended Crawler

```javascript
        for (const classItem of classes) {

            const classId =
                classItem.relationships

            if (!classId) continue;

            const meta = await getClassMeta(classId);

            const testIds = [
                meta.assignment?.test_id,

            for (const testId of testIds) {

                const problems = await getTestProblems(testId);

                for (const problem of problems) {

                    const submissions =
                        await getProblemSubmissions(

                        );

                }
            }
        }
    }
}
```

# 109. Do Not Fetch Every Test Configuration Unless Needed

Because:

```text
GET /api/v2/classroom/{class_id}/meta
```

already provides:

```text
assignment.test_id
homework.test_id
```

and:

```text
GET /api/v2/tests/{test_id}/problems
```

provides problem information, the crawler may not need:

```text
GET /api/v2/tests/{test_id}
```

for every test.

That would add an unnecessary request per test.

Potential efficient path:

```text
class meta
    ↓
test_id
    ↓
test problems
    ↓
user submissions
```

Use:

```text
GET /api/v2/tests/{test_id}
```

only if its additional metadata is actually required.

This can significantly reduce total API requests during historical backfill.

# 110. Request Count Optimization

Suppose there are:

```text
100 classes
```

and each has:

```text
1 assignment
1 homework
```

That could produce:

```text
100 classroom meta requests
200 test problem-list requests
many problem submission requests
```

The submission requests will dominate.

Therefore avoid redundant calls wherever possible.

For example, don't automatically call both:

```text
/tests/{id}
```

and:

```text
/tests/{id}/problems
```

unless both responses are needed.

# 111. Skip Empty Tests Where Possible

Class meta gives:

```text
solved
total
```

```json
"assignment": {
  "solved": 6,
  "total": 6,
  "test_id": 1226161
```

```text

```

the crawler may be able to skip fetching that test entirely.

Similarly, if an assignment/homework object is:

```text
null
missing
```

do not generate a request.

# 112. Potential Backfill Optimization Using `solved`

For the contribution calendar, the primary historical requirement is:

```text
successful solves
```

Class meta already tells us:

```text
solved count
```

Potential optimization:

If:

```text
solved = 0
```

and the only objective is reconstructing successful solve dates, then submission-history requests for that test might be skipped.

However, this would lose:

```text
failed attempt history
attempt statistics
language attempts
runtime-error history
```

Therefore there are two possible sync modes:

### Contribution-only mode

Skip tests with zero solved problems.

### Full analytics mode

Fetch attempted/unsolved problem histories too.

This product/performance tradeoff should be decided during implementation.

```text
    ↓
user submission
    ↓
created_at

historical solved date

Scaler++ contribution
```

This should now be treated as the primary technical foundation for the Scaler++ historical activity feature.
